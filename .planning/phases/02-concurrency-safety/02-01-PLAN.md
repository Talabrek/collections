Fix race condition where getProgress() returns null for recently joined players

Purpose: Players opening GUIs immediately after join currently see 0/0 progress because async load hasn't completed. This creates a poor user experience and data inconsistency.

Output: PlayerDataManager with getProgressBlocking() method, GUIs and commands that gate on data load completion with retry pattern.
</objective>

  <name>Task 1: Add getProgressBlocking() to PlayerDataManager</name>
  <files>src/main/java/com/blockworlds/collections/manager/PlayerDataManager.java</files>
  <action>
Add a new method `getProgressBlocking(UUID playerId)` that:

1. Fast path: Check cache first - if cached, return immediately (no blocking)
2. Check if load is pending: Look up `pendingLoads.get(playerId)`
3. If pending, block-wait: Call `pending.get(5, TimeUnit.SECONDS)` to wait for completion
4. On TimeoutException: Log at WARNING level with "Timed out waiting for player data load: " + playerId
5. On InterruptedException: Call Thread.currentThread().interrupt() and return null
6. On ExecutionException: Log at WARNING level and return null
7. If not cached and not pending: return null (player never loaded)

Method signature:
```java
/**
 * Get player progress, blocking if load is in progress.
 * Fast path: returns instantly if data is cached.
 * Slow path: waits up to 5 seconds if async load is pending.
 *
 * @param playerId The player's UUID
 * @return The player's progress, or null if not loaded/timed out
 */
public PlayerProgress getProgressBlocking(UUID playerId)
```

Do NOT change the existing getProgress() method - it remains non-blocking for internal use.
  </action>
  <verify>Compile: `./gradlew compileJava` passes with no errors</verify>
  <done>getProgressBlocking() method exists with fast-path cache check and 5-second timeout on pending loads</done>
</task>

  <action>
Modify the `open()` method in both GUI classes to gate on data load:

**CollectionMenuGUI.java:**
1. At the start of open(), call `playerDataManager.getProgressBlocking(player.getUniqueId())`
2. If returns null:
   - Send message: `player.sendMessage(configManager.getMessage("loading-data"))` (or fallback Component.text("Loading your collection data...", NamedTextColor.YELLOW))
   - Schedule retry using EntityScheduler: `player.getScheduler().runDelayed(plugin, task -> { if (player.isOnline()) open(); }, null, 20L);`
   - Return early (don't proceed with GUI)
3. If returns non-null: proceed with existing populateInventory() and open

**CollectionDetailGUI.java:**
Same pattern in open() method.

**Important:** Use `player.getScheduler().runDelayed()` for the retry, NOT Bukkit.getScheduler(). This is the Folia-compatible pattern from research.

**Fallback message:** If configManager.getMessage("loading-data") doesn't exist, use:
```java
Component.text("Loading your collection data...", NamedTextColor.YELLOW)
```
  </action>

Search code for "getProgressBlocking" to confirm both GUIs use it.
